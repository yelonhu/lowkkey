## 用户交付

首页饮食舱 → 选择日期／餐别 → 录入一餐及食物条目 → 查看原值、营养合计和未知项 → 修改／删除 → 明确确认当天完整度。只有描述时可保存为待完善草稿，随后补齐；草稿不计入营养合计。

首批同时交付手动营养、标签数据和小批受审参考食物。配方／常用餐、约100条完整目录、照片、AI、完整离线重开按既定后续批次推进，不用缩小范围替代这些要求。

## 已有实现与必须补齐的内容

- `src/server/meals.ts` 已实现餐食／描述草稿与冻结营养快照；`src/domain/manual-commands.ts` 已有 `meal.*`、`meal-draft.*`、`food.create`。页面继续经队列提交，不能直接 fetch 绕开幂等与版本保护。
- `PATCH /api/v1/days/:date` 已有服务端实现，**客户端仍缺日声明命令类型、版本绑定与 HTTP 映射**。客户端不可导入服务端模块；共享 schema 迁出时保留现有训练休息声明与幂等载荷语义。
- `nutritionReferenceSchema` 已有来源名、条目ID、URL、版本和获取时间；food 标准目录尚无六动作那样的审核元数据和发布种子。先固定需要记录的审核字段，再追加迁移；不重写旧 SQL。
- 编辑原餐食条目优先使用 `source: existing` 及条目 revision，继续使用冻结的 `nutrientBasis`；只有用户明确改来源／重算才换基准。新增项使用新ID，删除项及餐食根同事务变更。
- 手动输入要区分“所填数量对应的营养”和“每100 g／每份标签参考”。标签单位与份量基准要先明确，再按实际数量及摄入比例计算；避免表单把每份营养误作整餐营养。
- 复用精确十进制转换、`calculateItemNutrition` 和 `summarizeNutrients`；页面预览与服务端使用相同规则，事实以回执为准。ml 与 g 无明确密度不互换。
- 当前前端主块550.16 kB，gzip162.08 kB，已出现构建体积提示。接入饮食时评估领域按需加载；保留加载失败重试和已访问页面的草稿恢复，完整离线壳另行验收。

## 已复现的完整度并发缺口

在临时 D1 中复现，未触碰 `.data/dev`：

1. 设备A看到同日1餐，日声明为 unreviewed、revision=1。
2. 设备B新增第2餐；因为此前不是 complete，现有失效逻辑没有改变日声明，revision仍为1。
3. 设备A用旧revision确认 complete；当前服务端接受，将包含未见第2餐的当天标为 complete。

说明：现有“已确认后内容变化则失效”逻辑仍有效；**日声明 revision 本身不足以证明用户确认的是所见内容**。在完整度界面交付前，需增加同日内容版本校验，并覆盖首次声明、partial、unreviewed和重连的路径。确认后不得由队列静默改绑到刷新后内容。已保存的完整度不应因为其他日期或显示语言变化而失效。

证据：`.artifacts/m1-manual-diet-preflight/day-content-review.json`；复现脚本归档为同目录 `day-content-review.mjs`，使用项目隔离 Node、真实本地运行时与现有领域服务。结论是已复现的待修项，不计为业务通过测试。

## 必测场景

- **数值／来源**：参考每100 g的合成值按150 g且吃一半计算；未知宏量仍null；标签热量原值；生熟条目分离；无密度的ml转换拒绝；原值保留且存储只舍入一次。
- **修改／版本**：餐食根与条目revision一起校验；删除一项后合计更新；移动日期影响原日及目标日完整度；旧页面和旧撤销不覆盖新值。
- **完整度**：空日不显示0；显式零摄入；有待处理草稿时拒绝complete；content变化后partial；先前unreviewed/partial的旧内容确认也必须冲突。
- **本机／队列**：半份多条目表单刷新、对话往返、切语言不丢；失联后保留原操作ID；丢失回执先查；依赖失败保留候选；草稿确认不重复生成餐食。
- **隔离／交付**：跨owner不可读写；320／375／430px三语布局；原称重／训练回归；发布产物无测试身份或敏感配置。实机、人工目录审核、完整冷环境审计分别记录，不由自动化替代。
