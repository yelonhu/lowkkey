# M1 饮食便签 — 本地审阅交付

日期：2026-09-18。对应 SPEC v1.1.7，M1.6 第一批。**本批可审阅，整个 M1 尚未完成。**

## 现在可以体验

打开 [本地饮食页](http://127.0.0.1:5173/nutrition)，或从首页饮食卡进入。开发服务关闭时，在项目根目录运行 `./scripts/run dev`。首次进入沿用现有的本地虚构身份激活流程。

- 默认今天，也可选择过去日期。点“记一条”，写下吃了什么，离开整条便签后自动保存。
- 原文完整保留，不按标点拆食物，不推断克重、人数或比例。只有文字也是真实记录，不过期。
- 营养、餐别和实际时间按需展开；默认未知、仅日期。营养是这条记录本人实际吃下的部分，“吃了一半”不会再除以二。
- 编辑沿用同一记录；清空文字保留草稿并提示，删除必须明确操作。新增回执落账后提供10秒撤销，旧撤销不能覆盖后续修改。
- “今天记全了”是可选日级声明，和营养已知程度分开；本机还有修改时不允许确认。另一台设备改变当天内容后，旧声明必须重新核对。
- 首页先显示记录条数，有数字才显示已知热量。后台读取安静进行，离线显示已存本机，重连自动处理。

## 五分钟试用

1. 从首页饮食卡进入，点“记一条”，输入“小炒牛肉吃了一半、米饭一碗”。点击标题离开便签，等待就近的同步反馈；重新打开这一天，原话仍在。
2. 打开“补充营养”，填写热量 `350`、蛋白质 `20`，其他留空。在数字间切焦点不会提前保存；离开便签后更新同一条记录。合计是350 kcal，未知项仍显示“—”。
3. 添加第二条，只写“一杯牛奶”。可选点“今天记全了”，确认没有被要求补齐营养。再修改任一记录，状态变为“记录有更新”。
4. 输入尚未离开便签时直接刷新，确认草稿恢复；打开对话再返回，确认有效修改已保存且仍在原日期。切到过去日期试写，不会被搬到今天。
5. 在已打开页面断网，修改便签后离开，看到“已存本机”；恢复网络后自动同步。新建一条可测试10秒撤销；删除在详情内明确执行，清空文字不会删除。

第5步验证已加载页面的本机能力；本批**不承诺断网重新打开应用**。

## 工程实现与兼容

Meal 新增可空 `note`，保存原文、原始可空营养和计算快照。便签与食物明细互斥，汇总时各计算一次；旧明细记录和 v1 常用餐快照继续兼容，便签冻结为 v2 快照。没有虚构食物 ID、重量或“一份”。

所有写入沿用统一账本、稳定 ID、revision、幂等回执、事件与同步快照。新增 `day-claim.create/update` 类型化队列命令；按日 `nutritionContentRevision` 随相关内容变更在同一事务递增。确认携带所见内容版本，队列不能静默绑定新版本。候选明确转为记录和消费候选引用也同事务完成。

饮食代码独立于工作区入口，拆为页面、便签编辑、输入解析和本机投影。共享保存协调器串行处理提交；草稿消费与命令入队原子提交，慢存储期间新输入继续保留。原训练保存入口保留兼容转发，训练/体重共用新的编辑区事件。

追加迁移 `0010_diet_notes.sql`（含 Drizzle schema、snapshot 与 journal），只增加两列，不改旧迁移。日常开发数据先停止服务并备份，再在副本验证升级，之后应用到开发库；再次执行无变更。升级副本保留用户1、档案1、训练3、动作3、组6、体重4，原行逐列一致，外键检查为空；该副本没有旧饮食记录，旧明细/候选兼容由本地 D1 集成用例另行覆盖。

### 本次失败与修复

首轮 Worker 测试有一项把同步 schema 异常写成异步断言，修正后260项通过。首轮饮食浏览器用例的返回按钮定位不唯一，改为精确定位；完整回归中6个训练/体重竞态用例仍发送旧保存事件，更新为共同事件后126项通过。

视觉复核发现宽屏切窄屏时 textarea 高度未更新，增加宽度/字体变化下的自适应并验证原文无裁切。最终复核修正英文单复数、“营养未知”文案，并补充清空已有便签后禁止确认记全的保护；三语饮食另做21项定向复验。失败报告保留，未将失败轮次计为通过。
